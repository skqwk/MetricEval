# scheduler-sandbox

Среда имитационного моделирования для исследования алгоритмов планирования в предметной области сервисов-агрегаторов.

## Предметная область

Сервис-агрегатор принимает составные задачи от клиентов и выполняет их, последовательно отправляя подзапросы во внешний API. Внешний API ограничен глобальным лимитом RPM (requests per minute), который делится между всеми активными задачами. Планировщик решает, какая задача получает право отправить следующий подзапрос в каждый момент времени.

**Задача** — набор подзапросов `plan = [d₁, d₂, ..., dₙ]`, где каждый `dᵢ` — длительность подзапроса в секундах. Подзапросы выполняются строго последовательно: следующий начинается только после завершения предыдущего.

## Архитектура

Симуляция построена на событийной модели с тактовым генератором. Каждый такт (`MS_IN_ONE_TICK` модельного времени) все зарегистрированные акторы получают текущие сообщения и порождают новые.

```
TickMessage
  ├─→ TaskDequeActor         → NewTaskMsg (по мере прихода задач)
  ├─→ FastRequestCounterActor → ReadyRqMsg (если слот свободен)
  └─→ Scheduler              → завершение текущих подзапросов

ReadyRqMsg → Scheduler → StartRqMsg (выбор следующей задачи)
StartRqMsg → FastRequestCounterActor → обновление времени следующего слота

QueueEmptyMsg + пустая очередь → ShutdownMsg → конец симуляции
```

### Акторы

| Актор | Роль |
|---|---|
| `TaskDequeActor` | Высвобождает задачи по мере наступления их времени прихода |
| `FastRequestCounterActor` | Контролирует частоту запросов согласно RPM-лимиту |
| Планировщик | Выбирает задачу для следующего слота; вариант подставляется по алгоритму |
| `UtilizationActor` | Записывает метрики каждые 10 модельных минут |

## Алгоритмы планирования

### FCFS — First Come First Served
Задачи обслуживаются в порядке прихода. Простой и предсказуемый алгоритм, склонный к накоплению длинных задач в хвосте очереди.

### RR — Round Robin
Циклический перебор активных задач. Каждая задача получает слоты по очереди вне зависимости от объёма уже полученного сервиса.

### LAS — Least Attained Service
На каждый слот выбирается задача с наименьшим числом выполненных подзапросов. Минимизирует среднее время ожидания за счёт приоритизации «новых» задач над «тяжёлыми».

### HAS - Hybrid Adaptive Scheduler
Адаптивный планировщик, использующий `lookup_table.json` для выбора алгоритма с наименьшим отклонением от лучшего результата по эмпирическим метрикам.

## Метрики

Метрики записываются каждые 10 модельных минут.

### CV (Coefficient of Variation)
Оценивает неравномерность распределения сервиса между задачами.

Алгоритм (`p90-p50-window-200-lb-smooth-div2`):
1. Взять последние 200 задач по времени прихода.
2. Среди завершённых — собрать количество выполненных подзапросов.
3. Если завершённых < 10 — классический CV (σ/μ) по последним 100 задачам.
4. Иначе — `p90 / p50` распределения подзапросов.
5. Экспоненциальное сглаживание: `value = 0.3 × raw + 0.7 × prev`.

### Load (загрузка)
```
load = Q / (Q + 1) + max(trend / rpm, 0)
```
где `Q` — число активных задач, `trend` — сглаженная скорость роста очереди (α = 0.2). Значение > 1 сигнализирует о перегрузке.

## Формат входных данных

Каждый эксперимент располагается в директории вида:
```
dataset-generator/experiments/<num>/<scenario>/<run>/
```

**`dataset.csv`** — задачи (первая строка пропускается как заголовок):
```
arrival_time_seconds,"[duration1, duration2, ..., durationN]"
```
Пример: `0.0,"[5, 12, 8]"` — задача приходит в момент t=0 с тремя подзапросами длительностью 5, 12 и 8 секунд.

**`meta.json`** — параметры сценария (лежит на уровень выше, в директории `<scenario>/`):
```json
{ "rpm": 30.0 }
```

## Формат выходных данных

Для каждого алгоритма в директории прогона создаются три файла:

| Файл | Содержимое |
|---|---|
| `{ALGO}.csv` | Сводка по задачам: `task_id, start_sec, finish_sec, duration_sec, requests_count` |
| `{ALGO}_{метрика}_cv.csv` | Временной ряд метрики CV: `timestamp, tick, value` |
| `{ALGO}_load.csv` | Временной ряд метрики Load: `timestamp, tick, value` |

Файлы не перезаписываются при повторном запуске (идемпотентность).

## Параметры симуляции

| Параметр | Значение                    |
|---|-----------------------------|
| Шаг модельного времени | `${MS_IN_ONE_TICK}`         |
| Интервал записи метрик | `${INTERVAL_METRIC_RECORD}` |
| Параллелизм | по числу ядер процессора    |

## Запуск

**Требования:** Java ≥ 20

```bash
./gradlew bootRun
```

или

```bash
./gradlew build
java -jar build/libs/scheduler-0.0.1-SNAPSHOT.jar
```

`ExperimentRunner` рекурсивно обходит директорию `dataset-generator/experiments/<num>/`, находит все `dataset.csv` и запускает алгоритмы для каждого прогона параллельно.
